# 邀请关系与三代返佣（LC-018）

站内 USD 是充值和使用代币，不表示等值法币。本轮不计算支付现金与代币的汇率。

## 使用规则

- 每个用户均可充值、使用和邀请别人，无需切换角色。首次及后续有效充值均可产生返佣。
- 每笔余额充值按实际入账的 USD 代币数分佣；后台“管理员充值参与返利”开启时，“用户管理 → 充值”按所增加的代币数分佣。
- 正数余额兑换码参与返佣，用户手动兑换与外部支付集成的管理员自动兑换使用相同规则；以实际入账 USD 为基数，使用入账时的最近三代关系和比例，受返利总开关控制，不受“管理员充值参与返利”开关控制。
- 关联在线支付订单的兑换码由订单完成入口返佣，兑换入口不再重复计算。普通余额兑换码的消费、余额增加与佣金流水在同一事务提交，重复兑换不能再次返佣；流水来源显示“兑换码充值”。
- 独立赠额、设置余额、扣款、佣金转余额、负数余额兑换、并发兑换及订阅兑换不触发余额充值返佣。赠额沿用现有注册/优惠码设置，未另设金额。
- 顺着唯一 `inviter_id` 向上取最近三人；邀请链总长度不限。代次由与本笔充值者的距离决定，邀请别人不会改变自己的上游。
- 后台“设置 → 功能 → 邀请返利”分别配置一、二、三代比例。默认值从根目录 `affiliate-defaults.json` 生成；已有一级比例保留，缺失的二、三级配置取显式初始值。
- 默认 20% / 10% / 5%。D 入账 1,000 USD，C/B/A 得 200/100/50 USD；E 入账时最近三人改为 D/C/B。少一层就少付该层，比例为 0 的层仍占据自己的距离位置。
- 旧个人专属比例、累计上限和有效期不参与新规则；冻结期继续生效。旧字段和历史余额保留，设置个人比例的旧写接口提示改用三代设置。
- 返利总开关控制新返佣，不删除已绑定关系；关闭时注册关系仍记录。

## 统一邀请码

永久邀请码与 AFF 使用同一条邀请关系。关闭注册邀请码门槛时，可选邀请字段接受 AFF 或永久码；开启门槛时，仍需有效永久码或一次性注册码，普通 AFF 不能单独放行注册。永久码遵守状态、有效期和次数设置；预校验、邮箱注册、OAuth 首次注册共用解析逻辑。

在“永久邀请码”管理页创建或编辑返佣归属用户 ID。无归属的永久码仅用于注册；有归属的码消费成功时，在同一数据库事务内写使用记录、唯一直接邀请人和实际使用的码。

给已有永久码指定归属时，后台将历史使用者中未绑定邀请人的用户补入关系，并返回新增/跳过人数。已有 AFF 或永久码关系保持原样，历史充值不补发。归属变更也只影响尚未绑定的用户及未来注册；不会转移已有下级。

一次注册同时传入 `invitation_code` 和 `aff_code` 时，主邀请码先处理；如果已由永久码或 AFF 建立邀请关系，第二个码不覆盖、不重复计数。永久码也可从 `aff_code` 字段提交；同一注册重复提交同一码不再次消耗使用次数。旧的一次性注册码和无归属永久码仍可与一个 AFF 邀请人一起使用。

## API 与数据流

| 入口 | 行为 |
| --- | --- |
| `POST /api/v1/auth/validate-invitation-code` | 按注册门槛共用注册解析器：必填时只接受有效永久 / 一次性码，关闭门槛时可解析 AFF |
| `POST /api/v1/admin/reusable-invitation-codes` | 可选 `owner_user_id` 指定返佣归属 |
| `PUT /api/v1/admin/reusable-invitation-codes/:id/owner` | `{ "owner_user_id": 123 }`；返回 `code`、`bound_count`、`skipped_count` |
| 管理设置的 `affiliate_rebate_rate` / `_l2` / `_l3` | 一、二、三代百分比；独立存储并进入设置变更审计 |
| 用户邀请详情 | 返回 `rebate_rates_percent` 和带 `level` 的最近三代用户，邮箱继续脱敏 |
| 管理端返佣记录 | 代次、比例、本金快照；区分在线充值、管理员充值、兑换码充值和历史无订单流水 |

```text
永久码注册 / AFF 注册 → 唯一 inviter_id + 实际邀请码快照
余额充值入账 → 顺着 inviter_id 取三代 → 各自 USD 返佣流水与额度
在线订单：三代流水 + 订单 APPLIED/SKIPPED 标记一起提交
管理员充值：用户余额 + 调整记录 + 三代流水一起提交
普通余额兑换码：标记已使用 + 用户余额 + 三代流水一起提交
佣金转余额 → 只转移已有额度，不进入充值返佣入口
```

邀请绑定串行修改关系，阻止自邀请或环；历史补入会跳过已有关系及会形成环的绑定，不压缩代次。在线订单保留现有支付审计幂等协议，并以 `(source_order_id, user_id)` 唯一索引保证同一订单的同一收款人最多一条返佣。逐级计算还按用户去重；一层失败时整个返佣事务回滚。

## 迁移与运维

`268_affiliate_three_generation.sql` 为自有新迁移，无对应上游文件；以前的 SQL 不变。

| 数据 | 变化 / 回填 |
| --- | --- |
| `reusable_invitation_codes.owner_user_id` | 新增可空用户外键，历史永久码保持未分配，管理员显式选择归属 |
| `user_affiliates.invitation_code` | 新绑定保存实际码，历史缺失值不猜测；旧记录显示既有 AFF 码 |
| `user_affiliate_ledger.rebate_source / rebate_level / rebate_rate_percent / rebate_base_amount` | 新返佣保存来源、代次、百分比和 USD 代币基数，历史值保持 NULL |
| 订单收款人唯一索引 | 扫描返佣流水，建立单笔订单收款人去重；不删改历史金额 |

新增列和外键取得短时表锁；普通索引建立期间阻塞对应表写入并占用索引磁盘空间。启动时应由单个核心执行迁移，不运行新旧 writer。历史用户补绑定发生在管理员设置归属时，按码的使用记录增加邀请关系与邀请计数，不修改资金或 Redis 持久化。

升级前保留数据库备份；本地验收使用本地库备份，不使用生产库开发。旧程序虽然能忽略新增列，但仍按一级返佣并会忽略永久码归属，不是业务等价回滚。已有三代资金写入后保留当前数据向前修复，不只换回旧程序，也不用旧 dump 覆盖新数据。新增字段不要求运行环境参数或包外文件。

默认参数生成入口：`python3 tools/generate_affiliate_defaults.py`。根 JSON 和生成的 Go 默认值一起进入制品；日常比例在后台修改，无需重新构建。

兑换码返佣修复不新增 schema 或配置，沿用现有三代比例、冻结期和事务消费规则。仅修复上线后新发生的兑换；已使用兑换码不会通过重试补发历史佣金，历史补发需逐笔核对当时的关系、比例及已有流水后另行处理。升级前已创建但尚未使用的余额兑换码，在修复上线后兑换也按新规则返佣。回退旧程序会恢复普通兑换码不返佣的行为，已入账佣金保留。

本轮只通过正式包构建、启动及用户人工验收确认，不新增或运行自动化测试。需人工检查后台三档比例、永久码归属及补关系结果、用户三代列表和已存在业务流水；不为验收创建付费探针。


## 用户编辑中的邀请码换绑（LC-020）

管理员现在可以在用户编辑弹窗中按永久邀请码或 AFF 码查看、补绑和更换直接邀请人。当前邀请码关联与原注册来源分开保存，原三代规则、历史佣金及用户详情显示资格不变。换绑不修改码的所有者、不消耗注册码次数。管理员邀请列表显示当前关联码。

在线充值的受益链固定在实际入账事务，之后按该链和既有结算规则处理；管理员充值仍同事务完成。存量未返佣的已入账订单标记升级时关系基线，旧程序回退有语义限制。详见 [用户编辑中的邀请码与返佣归属](CUSTOMER_REASSIGNMENT_DESIGN.md)。
