# API Key 智能路由

智能路由让一个 API Key 按请求模型选择当前用户有权使用的分组。它不会授予额外分组权限，也不会自动把旧 Key 改为智能模式。

## 创建和切换

在 API Key 的创建、编辑或列表分组操作中选择“智能路由”。固定模式继续绑定一个具体分组；智能模式保存 `routing_mode=auto` 和 `group_id=null`。切回固定模式时应明确选择分组。

API 示例：

```json
{"name":"Unified key","routing_mode":"auto","group_id":null}
```

未传入路由模式的新 Key 默认使用 `fixed`。更新时省略字段表示保留原值；`auto` 与非空 `group_id` 同时提交会被拒绝。真正未分组的固定 Key 与智能 Key 是不同状态，列表筛选也分别处理。

## 分组选取与计费

1. 重新读取 Key、用户、团队生命周期、当前权限和分组配置。
2. 只保留付款主体有权使用且支持请求协议、模型和功能的分组。
3. 按管理员配置的模型优先级、默认分组优先级排序；未列出的候选按 `sort_order`、再按分组 ID 排序，选中第一个配置兼容的分组。
4. 携带实际分组审计原始请求，审计通过后执行最终资格、订阅、限额和计费准入。
5. 在选中分组内部沿用已有账号调度和重试逻辑。

选组不是最低价或最低延迟策略。选中分组的额度不足、瞬时容量不足或上游故障不会触发另一分组，也不会把订阅请求自动改为余额请求。

用量使用同一个 Key ID 累计，Key 的总额度和 5 小时、1 日、7 日额度不会按分组重新计算。实际分组的倍率、用户组倍率和平台配额继续生效，使用记录保留真实分组。团队 Key 使用团队付款主体的权限和订阅，同时保留实际成员归属。

同一模型在多个组出现时，优先级决定结果。模型公共别名、复合组路由和渠道映射按照现有模型配置处理。空账号模型映射不会让一个默认 OpenAI 组抢占所有供应商的模型；无法识别的平台部署别名应显式配置。

## 管理员模型优先级

管理员在“分组管理”的“智能路由优先级”中设置默认分组顺序，并为指定模型添加独立顺序。每个列表可增加、删除和上下移动分组。

规则使用公共模型名称：精确规则（如 `gpt-5`）优先于前缀规则；有多个前缀时使用最长匹配（如 `gpt-5*` 优先于 `gpt-*`）。未匹配规则的模型使用默认顺序。模型规则中未列出的授权组仍会按默认顺序及分组排序参与配置匹配；它是优先级设置，不是权限白名单。

示例：`{"default_group_order":[3,1],"model_rules":[{"model":"gpt-*","group_ids":[2,3]}]}`。同一 Key 的 GPT 请求依次检查 2、3、1 组的授权与配置；其他模型优先检查 3、1 组。组不属于用户权限范围时会被跳过。

配置通过管理员接口 `GET/PUT /api/v1/admin/api-keys/routing-policy` 持久化。规则只影响新的无状态选组；已有续链、连接和任务保留原归属。配置读取失败会明确报错，不能改用意外的顺序。配置保存不会重置 Key 用量。

参考源码为 New API 官方 main `eb99ab1b40343c3317bb47981cccdbb2b159a5fa`（2026-09-05）的 `service/group.go` 和 `service/channel_select.go`。本实现采用管理员有序候选的方式，不引入其可选的运行时跨组重试，也不声称自动按价格或延迟选择。

## 协议和目录

既有 Messages、Responses、Chat Completions、原生 Gemini、Embeddings 和支持的媒体入口使用同一 Key，沿用各协议的 URL。`/v1`、根路径别名、Codex 直连和 Antigravity 专用入口共享路由边界；强制平台入口仍限制实际平台。

- `/v1/models` 返回授权配置的模型目录，去重并稳定排序，不回退到全局账号或默认模型。
- Codex 模型请求保留 manifest 格式；每次先核验权限，再比较该次输出的 ETag。
- Gemini 模型目录仅包含该协议支持的授权模型。
- `/v1/images/batches/models` 返回授权批量模型及对应 provider。
- `/api/v1/keys/:id/routing-capabilities` 返回该访问者拥有的智能 Key 的协议与图片提交能力。
- 管理员对应接口是 `/api/v1/admin/api-keys/:id/routing-capabilities`，受既有管理员认证保护。

能力接口仅供界面展示，不保证当前容量或余额。实际提交仍完整鉴权。通配符和透传配置无法穷举所有名称，因此目录不是模型执行权限的唯一来源。

## 会话和任务

Responses 的 `previous_response_id` 必须能恢复同一物理 Key、成员、付款主体、团队、分组和账号的记录。记录使用共享 Redis 存储，过期或缺失返回 `AUTO_ROUTE_CONTEXT_REQUIRED`，存储故障返回 `AUTO_ROUTE_UNAVAILABLE`。不会枚举其他分组，也不会剥离 ID 后重放为新请求。

WebSocket 首帧选定分组，后续轮次保留组和会话账号，并复核 Key、团队、组权限和账号资格。每轮原始内容仍经过审计。停用 Key、撤权或不再兼容的模式变化会使连接后续请求被拒绝。

图片任务的历史列表、查询、删除和下载继续按原来的用户与 Key 拥有者授权，不为旧图片补造分组。新任务在创建前完成选组、审计和准入。

Live 和视频查询恢复已验证的原始归属。OpenAI 自动视频创建要求启用持久化视频任务生命周期。Grok 视频使用共享的 Key 归属索引恢复分组，索引与原有视频任务缓存保持相同 TTL，并保留创建时的订阅来源。

批量图片保存原始 `group_id`、账号和冻结价格。相同拥有者、Key 和幂等键的有效重试先返回原任务，不重新选组或预扣。现有批量计费只支持 Gemini 实体余额组，因此智能批量入口不把订阅组或复合组列为兼容候选。普通模型调用仍支持订阅组。

## 明确边界

- `simple` 运行模式不支持智能 Key，避免落入忽略分组的全局账号池。
- 单组 wham 额度视图不适用于智能 Key；`/v1/usage` 继续提供 Key 的累计用量。
- 没有可验证资源归属的供应商管理操作，以及无法恢复原上下文的视频派生入口，会返回上下文错误；不会尝试所有组。
- 切换 Key 路由模式后，旧会话如缺少智能归属记录，需要新建会话。
- 已成功生成后若归属索引写入失败，不重放生成请求；会记录不含原始内容或凭据的错误，之后的续链可能无法恢复。

## 升级与回退

数据库启动迁移自动执行 `253_api_key_smart_routing.sql` 和 `254_batch_image_routing_group.sql`。旧 Key 默认 `fixed`，旧批量任务的分组保持 NULL。模式变更会更新认证缓存版本并触发缓存失效。

生产启用前，应先让所有服务实例升级到识别新字段的版本，再创建少量智能 Key 验证实际分组、账单与审计记录。不要让旧实例处理 `auto` Key。

回退应用前，先停用智能 Key，或将其明确改回固定分组。保留新增迁移和历史数据，不修改已有迁移 checksum，不删除历史任务归属。发布和生产数据调整需要独立的操作授权。
