## 1. 要解决的问题

推广人 A 实际邀请了客户 B，但 B 注册时漏填推广码、使用通用入口，或者误填了其他推广人 C 的推广码，导致系统中的返佣归属不符合真实业务关系。

本提案拟新增“调整客户归属”能力，允许管理员在注册后为 B 指定正确的推广人 A。调整成功后，B 新发生且符合现有返佣条件的业务，按 A 的返佣比例结算；原有佣金通过历史账本保留。

示例：B 原来属于 C。管理员将 B 调整给 A 后，B 成为 A 的当前直属客户；此后符合规则的新充值给 A 返佣。C 过去从 B 获得的佣金仍归 C，能够继续在历史返佣记录中查询。

## 2. 提案范围与推荐业务规则

| 类型 | 内容 |
| --- | --- |
| 功能范围 | 支持注册后补绑客户，也支持从任意错误推广人转给指定用户。 |
| 权限范围 | 普通管理员也可以操作，不限站长或超级管理员。 |
| 推荐默认值 | 只影响生效后的返佣；不自动补发、扣回或重分配历史佣金。该项是供业务评审的建议，尚非既定结算政策。 |
| 推荐默认值 | 以平台成功入账／权益成功发放时的归属确定受益人，不以下单时间或延迟返佣的执行时间决定。 |
| 推荐默认值 | 调整必须填写原因，保留完整业务变更记录。 |
| 推荐默认值 | 有效期不重置；同一客户在各推广人名下的已产生佣金共同占用单客户上限。 |

本文围绕上述推荐规则给出待评审方案，所述接口、字段、事务和页面均为拟议设计。历史补佣如果后续需要，应另行设计逐笔调整流程及资金影响明细。

## 4. 功能行为

### 4.1 支持的操作

| 当前关系 | 操作 | 结果 |
| --- | --- | --- |
| B 无推广人 | 指定 A | B 归属 A，A 当前客户数加一。 |
| B 通过通用入口注册 | 指定 A | 根据实际现存关系执行补绑或转移，不将“通用码”假设成一个固定系统用户。 |
| B 归属 C | 改为 A | B 归属 A，C 当前客户数减一，A 加一。 |
| B 已归属 A | 再次指定 A | 返回“归属未变化”，不产生重复业务变更。 |
| 上次将 B 从 C 调给 A 后发现操作错误 | 再将 B 从 A 调回 C | 形成新的反向调整，从本次生效时间起归 C，保留前后两次记录。 |

首版只处理单个客户到一个指定用户的补绑或转移。清空归属、批量转移、下级客户整体迁移不在首版范围内。从无归属错误补绑后的“恢复为空”也不包含在首版，不能通过向调整接口传入空目标绕过有效用户校验。

### 4.2 返佣与历史资金

1. 调整前已产生的佣金保留原受益人，包括冻结中、可用和已转入余额的部分。
2. 调整不发放注册奖励，不改变客户余额，也不把原推广人的佣金余额转给新推广人。
3. 生效后的合规业务使用 A 的有效返佣比例。比例为零、返佣关闭、有效期届满或达到上限时，客户可以调整成功，但该业务仍可能没有返佣。
4. B 的返佣资格期限连续计算，换绑不会恢复已用时间。已有推广档案保留原起算时间；历史无档案用户以用户注册时间作为补绑资格起点，不能以管理员操作当天重新起算。
5. 单客户上限按 B 在所有受益人名下的累计 `accrue` 金额计算。冻结佣金已属于产生的佣金，应占用上限；转入余额不再次计入。
6. 历史记录已超过新口径上限时，不追扣历史金额，后续返佣额度为零。历史补发、冲回及退款返佣规则不随本功能隐式新增。
7. 当前核查的返佣服务只处理直属邀请人。B 自己邀请的客户仍归 B，B 作为推广人的专属比例和推广码保持其自身语义。

累计上限以可追溯到 B 的逐笔账本为核算依据。若历史佣金早于账本机制，且只有推广人总额而没有来源客户明细，不能仅凭 `aff_history_quota` 还原 B 的完整累计金额。上线核查应记录这类数据缺口；有可靠逐笔证据时导入可审计的基线，没有证据时明确只能计算现有账本覆盖的金额，不能宣称已还原全部历史支出。

### 4.3 生效时点

“生效”以归属调整事务成功提交为准；每笔业务以平台成功入账／权益发放的事务为归属判定点。

| 时间顺序 | 返佣归属 |
| --- | --- |
| 调整前下单，调整后才成功入账 | A。 |
| 调整前已经入账，调整后才执行返佣或重试 | 入账时的旧归属。 |
| 入账时没有推广人，后续补绑 A | 该笔业务仍按无推广人处理，后续新业务可归 A。 |
| 支付与调整同时发生 | 由数据库对 B 归属的串行化顺序确定，得到唯一结果。 |
| 支付平台显示成功，但平台尚未到账 | 按平台实际成功入账时的归属处理。 |

不能仅在返佣执行时读取 B 最新的 `inviter_id`。归属快照必须和对应的到账／权益发放在同一个事务中持久化；重试使用已保存的快照。

## 5. 管理员操作流程

主入口：用户管理 → 找到 B →“调整客户归属”。辅助入口：当前邀请关系列表中的客户行操作。

必须提供用户管理入口。现有邀请列表不包含无邀请人的用户，仅在该列表增加按钮无法覆盖漏绑客户。

### 5.1 调整弹窗

| 项目 | 交互要求 |
| --- | --- |
| 客户 | 展示 B 的 ID、用户名、邮箱和账号状态。 |
| 当前归属 | 展示现有推广人的身份信息；无归属时明确显示“暂无归属”。 |
| 新推广人 | 支持按用户 ID、用户名或邮箱定位，选择后展示唯一用户 ID 供核对。复用并按需扩展已有用户搜索。 |
| 原因 | 必填；去掉首尾空白后 1—500 个字符；作为业务记录保存。 |
| 规则摘要 | 展示新推广人的有效比例，以及客户当前是否超出有效期或已达到返佣上限。 |
| 生效说明 | 明确本次影响未来业务，历史佣金保留。 |

确认内容示例：

> 将客户 B（#208）的归属从 C（#31）调整为 A（#17）。调整生效后成功入账、且符合返佣规则的新业务，将按 A 的有效比例计算。此前产生的佣金保留原记录。

提交按钮使用“确认调整”，提交期间禁用。成功后刷新 B 的归属、涉及推广人的当前客户数及变更历史。遇到归属版本冲突时，保留填写的原因并要求刷新确认新的当前归属。

### 5.2 权限与校验

- 复用现有管理员鉴权，普通管理员可操作；普通用户无修改与管理历史查询权限。
- B 必须存在且未删除；A 必须存在、未删除且处于有效状态。
- 禁止 B 指向自己，禁止形成直接或间接循环关系。校验必须在服务端完成。
- 验证失败、数据库失败或审计业务记录写入失败，整个调整事务回滚。
- 操作人从可信认证上下文获取，不能接受客户端自报的管理员 ID。复用管理 API Key 时记录真实认证方式，不将共享凭证操作伪装成某位具名管理员。

## 6. 接口设计

以下是拟新增接口，不代表仓库当前已存在。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/v1/admin/affiliates/users/:user_id/inviter` | 读取当前归属、专用关系版本、生效时间及展示所需的规则摘要。只读查询不应因查看而创建推广档案。 |
| `PUT /api/v1/admin/affiliates/users/:user_id/inviter` | 补绑或调整归属。 |
| `GET /api/v1/admin/affiliates/users/:user_id/inviter-changes` | 分页查询该客户的业务变更记录。 |

请求示例，所有 ID 均为虚构示例：

```json
{
  "new_inviter_id": 17,
  "expected_version": 2,
  "reason": "客户误填推广码，经核实应归属 A",
  "request_id": "d7a68aad-4ef0-4caf-8fb0-3b9fe33fb156"
}
```

成功响应沿用项目统一响应包装，业务数据包含 `changed`、`user_id`、`previous_inviter_id`、`inviter_id`、`version`、`effective_at`、`change_id`。

- 相同请求 ID 和相同有效载荷重试，返回第一次结果，不重复变更、计数或留痕；相同请求 ID 携带不同载荷返回冲突。
- 持有旧版本的请求返回 `409 AFFILIATE_RELATION_CHANGED`，即使期间经历了 A → C → A，也不能把最终 ID 相同当作关系从未变化。
- 在版本匹配的情况下，新旧推广人相同返回 `changed=false`。
- 无权限返回 403，用户不存在返回 404；自我绑定、循环关系、无效目标和原因格式错误返回可翻译的业务错误。

## 7. 数据和事务设计

### 7.1 当前归属

继续使用 `user_affiliates.inviter_id` 作为当前关系的唯一真源。建议扩展以下字段：

| 字段 | 语义 |
| --- | --- |
| `inviter_version` | 只在归属发生变化时递增的版本，初值 0。不能复用会随金额变动的 `updated_at`。 |
| `inviter_effective_at` | 当前关系明确生效的时间；无法还原的旧绑定时间保留为空，界面展示“历史绑定时间未记录”。 |
| `rebate_started_at` | 返佣资格起点。已有档案从原 `created_at` 回填；历史无档案用户补建时采用用户注册时间。 |

既有 `aff_count` 统一解释并展示为“当前直属客户数”。本次迁移需要按真实关系校准计数，并同步更新相关注释、接口说明和中英文界面文案；不能继续标成“累计注册邀请人数”。

### 7.2 业务变更记录

建议新增 `user_affiliate_inviter_changes`，记录客户 ID、原推广人 ID、新推广人 ID、前后版本、操作人及认证方式、原因、请求 ID、服务端生效时间。用户删除后仍保留足以解释变更的身份快照，避免级联删除抹掉业务记录。

该记录与归属调整在同一事务写入。通用管理员操作审计继续保留，但不替代业务变更表，因为通用审计存在清理和保留期机制。

业务界面不提供编辑或删除历史变更的操作。原推广码的注册输入没有可靠历史证据时，不以当前推广码反推。

### 7.3 入账归属快照

建议新增 `affiliate_rebate_attributions`，按业务来源固定一次归属，最小字段包括：

| 字段组 | 内容 |
| --- | --- |
| 来源 | `source_type`、`source_id`，组合唯一。支持支付订单和独立正数余额兑换。 |
| 归属 | 客户 ID、可为空的受益人 ID、归属版本、平台入账／权益发放时间。 |
| 规则 | 当时的有效比例、资格判定及无返佣原因。金额使用与现有账本一致的十进制定点精度。 |
| 处理状态 | 待处理、已返佣或已跳过，并可关联实际资金账本；终态不能因为换绑而重新处理。 |

无推广人也必须保存明确的已判定结果，不能用空受益人同时表示“尚未读取归属”和“已确认没有推广人”。

在线余额订单在内部使用兑换码到账时，以支付订单作为唯一来源，并继续抑制兑换码级重复返佣。独立余额兑换使用兑换记录 ID，不保存或展示原始兑换码作为幂等标识。套餐订单在权益发放事务中固定归属；不新增原来没有返佣的业务类型。

此表承担归属固定和处理追踪，不引入新的消息队列或通用任务框架。后续处理和重试应复用现有业务路径，并以来源唯一性防止重复结算。

### 7.4 原子性与并发约束

一次归属调整必须原子完成：验证关系版本 → 校验目标和关系环 → 修改 B 的归属 → 更新 C、A 的客户数 → 写入业务变更记录。

归属调整、注册绑定和入账快照使用一致的数据库并发协议。行锁按确定顺序获取；涉及关系环的判断需要覆盖并发的跨用户调整，仅锁 B 一行不足以阻止同时形成循环。具体锁协议须在实现阶段以交叉转移测试验证。

返佣结算对同一个 B 串行校验累计上限；检查上限、额度增加、账本落库和来源状态变更必须处于同一事务，避免两笔不同订单并发超过上限。客户已用额度从历史账本累计，不因受益人更换或资金解冻而恢复。

## 8. 页面与统计口径

| 展示项 | 新口径 |
| --- | --- |
| 当前客户列表 | 根据当前 `inviter_id` 展示。 |
| 当前直属客户数 | 与当前关系一致，转移时一减一增。 |
| 当前客户贡献佣金 | 该客户历史上实际发给当前查看推广人的金额；不能把旧推广人的金额搬过来。 |
| 历史累计佣金 | 按资金账本实际受益人累计，转移不修改。 |
| 历史贡献返佣客户数 | 按历史账本来源客户去重，允许大于当前客户数。 |
| 归属生效时间 | 展示专用关系时间；不将注册或推广档案创建时间冒充本次调整时间。 |
| 归属变更历史 | 管理员按客户查看功能启用后的完整变更链及可证明的迁移基线；普通用户不获得管理员原因及其他推广人的客户信息。 |

现有“邀请记录”应明确为“当前客户归属”或同义文案。C 的当前客户列表移除 B 后，C 的历史收益仍可解释，管理端可以沿历史账本查询到当时的来源客户。

## 9. 存量数据与实现范围

只新增向前迁移，不修改历史 SQL 迁移文件。按实施时仓库最新编号分配迁移编号；涉及 Ent／Wire 时按仓库规范重新生成，不手改生成文件。

迁移需要处理三类数据：

1. 当前关系：初始化专用版本与资格起点，校准当前客户数；未知历史关系时间保持未知，不编造注册邀请事件。
2. 已产生返佣或已明确跳过的业务：保留原账本和终态，不能因为功能上线补发。
3. 已入账但返佣尚未完成的业务：在允许管理员调整归属前，按可靠的原有数据确定受益人并初始化快照；无法证明原归属的异常业务需进入待核查状态，不能在换绑后读取当前关系当作历史事实。

部署顺序应先完成字段、快照写入路径和存量处理，再启用管理入口，避免旧版本实例继续写入没有快照的到账记录。回退应用版本前，应先关闭调整入口并保留新增数据，不能依靠删除变更历史完成回退。

拟涉及的模块：

- 后端 affiliate handler、service、repository 与 admin routes。
- payment fulfillment、redeem service 和相关订单／权益发放事务。
- 数据迁移、必要的 schema、接口实现、stub 与 mock。
- 管理员用户页面、邀请关系表、调整弹窗、管理 API 类型和用户端相关统计文案。
- 归属行为与接口文档、中英文 locale、相关测试。

## 10. 验收清单

以下均为计划验收项，尚未运行。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| A01 | 无归属 B 补绑 A | 后续合规业务给 A 返佣，客户数只增加一次。 |
| A02 | 通用入口或错误推广人 C → A | 正确处理实际旧关系，双方计数和列表一致。 |
| A03 | A 有专属比例／无专属比例 | 分别使用 A 的专属比例／全局比例。 |
| A04 | 调整前已有冻结、可用、已转余额佣金 | 原受益人的历史记录及金额保留。 |
| A05 | 调整前下单、调整后到账 | 使用 A。 |
| A06 | 调整前到账、调整后返佣或失败重试 | 使用到账时的旧归属；无归属快照不得补成 A。 |
| A07 | 两个管理员同时修改 B，或 A → C → A 后提交旧请求 | 返回明确版本冲突，不覆盖他人操作。 |
| A08 | 重复请求、相同请求 ID 不同载荷 | 前者返回原结果，后者冲突；不重复计数或记账。 |
| A09 | 支付重复回调、余额订单内部兑换 | 一笔业务最多产生一次返佣。 |
| A10 | 两笔不同业务同时接近 B 的单客户上限 | 在可追溯账本及可靠基线范围内，合计不超过剩余额度；C → A 不恢复额度，历史缺口明确记录。 |
| A11 | 返佣已过期、历史无档案老用户补绑 | 不因换绑或临时建档重新获得有效期。 |
| A12 | 普通管理员／普通用户分别调用接口 | 管理员允许，普通用户拒绝。 |
| A13 | 自我绑定、无效目标、直接或间接循环，以及并发交叉绑定 | 服务端拒绝，关系及计数保持一致。 |
| A14 | 事务中途失败或业务变更记录写入失败 | 关系、计数和变更记录整体回滚。 |
| A15 | B 自己已有直属客户 | 下级客户仍归 B，B 自身推广设置语义不变。 |
| A16 | 反向调整和历史统计 | 两次变更都可追溯，历史收益不随列表变化消失。 |
| A17 | 返佣关闭、零比例、金额或资格不符合现有条件 | 调整可成功，返佣按既有业务资格跳过。 |
| A18 | 升级前已完成、已跳过、已到账待处理业务 | 不重发终态业务；待处理业务使用可靠初始化的原归属。 |
