# 用户编辑中的邀请码与返佣归属（LC-020）

本文描述当前统一邀请码换绑行为；历史迁移和账务语义保持不变，发行与生产状态由运维记录独立确认。

## 管理员怎么操作

打开“用户管理 → 编辑用户”，在用户名下方查看“邀请码与返佣归属”。面板显示当前推广人的用户名、邮箱与 ID，并填入当前关联的邀请码。

输入一个新邀请码，点击「解析归属」核对推广人，再点击弹窗底部「更新」，无需选择码类型。新归属与本次基础资料一起保存；解析不会修改数据。没有邀请人的客户也能这样补绑。

邀请码必须已经绑定推广人。换绑不消耗注册码次数，因此不以注册码剩余次数或有效期决定既有客户的归属调整。推广人必须存在且有效；不允许归属自己或形成邀请环。

这里改变的是客户的当前邀请码关联和直接邀请人，不修改永久码的所有者或客户自身用于邀请他人的默认码。暂不提供清空归属、批量转移、历史补佣或扣回操作。

## 返佣与历史

当前关系仍只有一个真源：`user_affiliates.inviter_id`。当前关联使用新增 `attribution_code_type` / `attribution_code`；原 `invitation_code` 和永久邀请码使用记录保留注册时含义。

变更后新的有效充值沿最近三代关系计算；B 自己邀请的 D 仍直属 B，但 D 后续充值在最近三代内经过的推广人可能随 B 换绑而改变。页面在保存前说明这一点。

已经产生的冻结、可用、已转入余额佣金及原受益人均保留。比例、返佣开关、冻结期限继续采用既有结算时读取的规则；本功能固定的是受益链，不新增返佣业务类型，不恢复旧个人专属比例、有效期或单客户上限。

## 原子提交与接口

| 方法与路径 | 行为 |
| --- | --- |
| `GET /api/v1/admin/affiliates/users/:user_id/inviter` | 只读获取当前邀请码、类型、推广人、关系版本及已记录生效时间；查看不创建推广档案。 |
| `POST /api/v1/admin/affiliates/inviter/resolve` | 接受 `code`，从统一目录只读解析推广人；历史 `code_type` 可省略，不再选择不同目录。代码放在请求体，沿用现有请求体 code 字段脱敏。 |
| `PUT /api/v1/admin/users/:id` | 在原用户编辑请求中接受可选 `inviter_change`。 |

`inviter_change` 包含 `code`、`resolved_user_id` 和 `expected_version`。操作者 ID 与认证方式由服务端设置，不接收客户端提供的操作者信息。

保存从统一目录重新解析邀请码，并核对前端展示的归属用户；码的拥有者发生变化时返回 `AFFILIATE_CODE_OWNER_CHANGED`。客户关系版本不一致时返回 `AFFILIATE_INVITER_CHANGED`，不覆盖别人的更改；用户须重新打开编辑窗口获取真实状态。同一目标及同一码不重复更新。

关系、当前关联、双方直属客户数、关系版本和 `affiliate_inviter_changes` 记录在同一事务写入，并和基础资料更新共享事务。版本递增覆盖首次绑定和之后的调整，A → B → A 也会被识别为发生过变化。原有自定义用户属性仍由原独立接口保存。

复用 `affiliate_inviter_binding` 事务锁，覆盖首次注册绑定、永久码关联、AFF 码修改、换绑和返佣链读取。充值先取得该关系锁，再修改余额，避免读取到混合的三代关系。普通管理员使用既有管理鉴权；管理 API Key 记录实际认证方式，具名操作者字段为空。

## 在线充值的受益链

有效余额订单通过兑换码实际入账时，在同一事务写入 `affiliate_payment_attributions`，包含订单、客户、最多三代的受益用户 ID、时间与来源。没有邀请人也保存空链，之后补绑不会把这笔已入账订单转给新人。该步骤处于共同兑换入口，在线履约或用户兑换同一支付码均固定一次。普通正数余额兑换码没有支付订单，在兑换事务内按一致的当前关系直接完成三代返佣，消费记录、余额和佣金整体提交，不创建支付订单快照。

支付履约的后续返佣读取保存的受益链，沿用既有订单幂等标记与三代账本事务。快照缺失时明确报错，不用最新关系冒充原关系。管理员充值继续在原充值与返佣事务内读取一致的当前链。

## Migration 271 与存量

`271_affiliate_inviter_reassignment.sql` 增加当前关联、关系版本和生效时间，新增业务变更表及支付受益链表；这些沿用原 AFF 的 SQL repository 管理方式，不手改 Ent 生成文件。

初始关联优先使用与现有邀请人匹配的原永久邀请码，否则采用邀请人的 AFF 码。旧绑定时间没有可靠记录，保留为空，不拿注册时间冒充。

对升级前已入账但尚未返佣的旧订单，在管理员能够换绑前，固化**升级时的当前关系基线**并标记 `legacy_upgrade`。它不是历史入账时快照；无法追溯的过去不被声明为已还原。已完成或明确结算/跳过的订单不重新返佣。

迁移会更新已绑定用户的当前关联字段，并扫描及固化必要的旧待结算订单。DDL 持有表锁，回填产生 WAL，新增数据和索引占用空间与用户及待结算订单数量有关。没有历史资金改写，没有 Redis 格式变化或新增运行配置。

部署保持单 writer，迁移前备份。换绑或生成新快照后，旧程序会忽略新的受益链，无法保证延迟订单归属；不能仅退回旧二进制。保留当前数据并前向修复，也不能用旧备份覆盖新的资金写入。

本地实际操作结果由运维工作区 `docs/history/` 记录。人工验收后仅发布同一正式包，生产更新仍由用户从自有发行通道完成。
