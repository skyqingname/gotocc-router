## 1. 问题与范围

客户 B 漏填或误填邀请信息后，管理员目前无法纠正注册后的直接邀请人。本提案讨论单个客户补绑或更换直接邀请人；普通管理员权限、操作原因、未来生效且不追溯历史佣金，均为待业务确认的建议。

示例：B 原直属 C，调整为 A 后，B 的新充值沿 A 的上游链按最近三代计算。历史佣金保留账本中的原受益人，包括冻结中、可用和已转入余额的金额。

首版拟不包含历史补佣、扣回、清空归属、批量转移或直接重写下级客户关系。从无归属补绑后“恢复为空”也不在拟议范围；实施前应确认这一限制。

## 2. 必须保持的现有规则

以下来自已发行代码和运维工作区 LC-018；不是本提案新增政策。

| 现有行为 | 对换绑设计的约束 |
| --- | --- |
| 永久邀请码的归属用户与 AFF 共用 `user_affiliates.inviter_id`，首次绑定保留唯一直接邀请人。 | 调整该唯一关系，不修改注册准入码、永久码使用记录或原始来源字段。不能让后续永久码关联回填覆盖已调整关系。 |
| 关系链可以延伸，每笔有效充值只向最近三代返佣。 | 快照保存最多三代受益人，不能只保存 A。缺失层级不补给其他人。 |
| 三代比例使用后台全局配置，初始参数为产品根目录 `affiliate-defaults.json` 的 20%、10%、5%。 | 换绑沿用每代配置；旧个人专属比例、旧有效期和旧单客户上限不适用于现行三代规则，不借此恢复。 |
| 计费基数是实际入账的站内 USD 代币。 | 不按支付现金金额、汇率或独立赠额计算。 |
| 在线有效余额充值参与返佣；管理员“充值”仅在既有管理员充值返佣开关开启时参与。 | 两类入口都需要确定归属时点；设置余额、扣款、独立兑换、赠额、套餐权益、佣金转余额不因换绑而获得返佣资格。 |
| 支付订单的所有上游返佣及订单幂等标记在同一事务中提交。 | 保留这项原子性；同一订单每代最多结算一次。 |
| 统计卡片、三代说明和最近三代名单只向永久邀请码的现存归属用户展示。 | 换绑不改变 `show_rebate_details` 的判断，也不额外授予查看资格；展示限制不改变获得佣金的资格。 |

如果 B 有下级 D，D 的直接邀请人仍是 B，但 B 换绑会改变 D 及部分更深下级未来充值在最近三代内经过的祖先与受益人。提案不能承诺“只影响 B 的充值”。这一实际影响必须在业务评审和管理员确认界面披露。

## 3. 推荐行为与生效时间

| 操作 | 推荐结果 |
| --- | --- |
| B 无邀请人 → A | 建立唯一直接关系，A 当前直属客户数增加一次。 |
| B 原直属 C → A | B 指向 A，C 当前直属数减一，A 加一。 |
| B 已直属 A → A | 版本一致时返回未变化，不重复计数或记历史。 |
| A → C 的反向调整 | 创建新的变更记录，从新生效点影响未来业务；不删除旧记录。 |

推荐以归属调整事务提交作为关系生效点，以实际充值入账事务固定返佣归属及当时三代规则。该时点选择仍待业务确认；目前服务在返佣时遍历关系，不能宣称已有入账时完整快照。

| 时间顺序 | 推荐归属 |
| --- | --- |
| 调整前下单，调整后成功入账 | 按入账时的新三代链。 |
| 调整前入账，调整后返佣或重试 | 保留入账时的三代链及比例。 |
| 入账时没有邀请人，之后补绑 | 原业务保持无返佣结论，只影响后续合规业务。 |
| 入账与任一相关祖先的归属调整并发 | 用统一数据库串行化协议确定完整三代链，不能混用两次关系版本。 |

推荐不追溯历史佣金、不改变客户和推广人余额、不补发注册奖励。返佣关闭、某代比例为零或业务不符合资格时，调整本身可成功，返佣仍按现有规则处理。

## 4. 管理入口与接口草案

主入口建议放在“用户管理”的客户行，兼容没有邀请人的用户；已有邀请列表可提供辅助入口。弹窗展示客户身份、当前邀请人、新邀请人的唯一用户 ID、原因、最近三代的新旧链，以及对下级未来返佣的影响。原因建议去掉首尾空白后为 1—500 个字符，具体上限实施时放入根参数文件。

建议普通管理员可以调整，普通用户不可修改或查询管理历史。操作者取自认证上下文；管理 API Key 操作记录实际认证方式，不伪装成某位具名管理员。目标须存在且有效，不得自指或形成直接、间接循环。

以下接口均未实现：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/v1/admin/affiliates/users/:user_id/inviter` | 只读获取当前关系、专用关系版本、生效时间和三代规则摘要；查看不创建推广档案。 |
| `PUT /api/v1/admin/affiliates/users/:user_id/inviter` | 补绑或更换直接邀请人。 |
| `GET /api/v1/admin/affiliates/users/:user_id/inviter-changes` | 管理员分页查看业务变更历史。 |

请求拟包含 `new_inviter_id`、`expected_version`、`reason`、`request_id`。同一请求 ID 和有效载荷重试返回原结果，不同载荷返回冲突；旧关系版本返回 409，即使期间经历 A → C → A。成功数据包含是否变化、前后邀请人、关系版本、生效时间和变更 ID，沿用统一响应包装。

## 5. 数据与事务草案

继续以 `user_affiliates.inviter_id` 为唯一当前关系，建议增加 `inviter_version` 和 `inviter_effective_at`。旧关系的真实生效时间无法证明时保留未知。无需为已退役的资格有效期新增 `rebate_started_at`，也不新增或回填旧单客户上限。

建议独立记录不可在业务界面编辑的归属变更历史：客户、前后邀请人、前后版本、操作者及认证方式、原因、请求 ID、生效时间。与关系和双方直属客户数在同一事务写入；通用操作日志不能替代业务历史。

入账归属快照应按业务来源唯一保存一次，包含：

- 来源类型与稳定的来源 ID；覆盖在线有效余额充值和开关允许的管理员充值。
- 客户、实际入账代币金额、入账时间、明确的资格判定和无返佣原因。
- 最多三代的受益人、层级、关系版本、比例与应计金额；无上游或零比例仍保留明确结果。
- 处理状态和实际账本关联；重试沿用快照，终态不因换绑重新处理。

余额订单内部使用兑换码入账时仍以订单为来源；独立兑换不返佣，不引入兑换码级第二次分佣。管理员充值使用其稳定业务记录 ID，具体字段待实现时核查；本提案不虚构已有幂等字段。

快照与充值入账必须在同一事务固定，所有三代结算仍在同一结算事务内提交。若现有入口无法共享事务，需在实施设计中先解决，不能以异步补读最新关系代替。

归属调整、注册绑定、永久码归属关联回填和入账快照必须使用一致的并发协议。只锁 B 无法阻止跨用户并发形成循环，也无法确保祖先同时换绑时读取一致的三代链。具体锁顺序、锁范围和延迟影响待实施设计明确，不在文档中假定已经解决。

## 6. 统计和存量兼容

`aff_count` 建议明确为当前直属客户数，按实际关系核对并同步相关注释与界面。当前列表来自当前关系；历史贡献佣金和累计收益来自账本的真实受益人，不把旧推广人的收益搬给新推广人。

原注册输入和永久码使用记录保持历史语义，不用当前推广码反推。当前归属生效时间单独展示；普通用户不获得管理员原因或其他推广人的私有客户信息。

只新增向前迁移，不修改历史 SQL。实施前披露迁移 lineage、锁与磁盘影响、回填、旧程序兼容和回滚限制。旧关系时间未知就保持未知；已结算或已跳过的业务保持终态。对已入账待处理的业务，先根据可靠数据初始化原三代归属；无法证明的须明确待核查，不能以当前关系冒充历史快照。

需先部署完整快照写入与存量处理，再启用管理入口；新旧 writer 不重叠。启用调整后旧程序可能按最新关系结算延迟订单，关闭入口并不自动解决旧程序兼容。不得宣称仅换回旧二进制就完成资金或关系回滚。

## 7. 计划人工验收

以下均未执行，实施时按本地最终包运行并交用户验收，不以本提案合并作为功能验收。

| 场景 | 预期 |
| --- | --- |
| 漏绑、误绑、重复指定同一邀请人 | 唯一关系、计数、列表一致。 |
| 完整三代链、缺失层级和零比例 | 沿用后台三代规则，不恢复个人比例、有效期或上限。 |
| B 已有下级 | 直接关系不批量改写；下级未来三代受益链变化符合披露。 |
| 已有冻结、可用、已转余额佣金 | 原受益人、金额和历史保持不变。 |
| 先下单后调整再入账、先入账后调整再重试 | 分别使用新快照、原快照，未绑定业务不被追补。 |
| 在线充值、管理员充值开关开关两态 | 按实际入账代币和既有业务资格处理。 |
| 独立兑换、赠额、设置余额、扣款、套餐、佣金转余额 | 不新增返佣。 |
| 重复回调、请求重试和同 ID 不同载荷 | 不重复归属变更或三代结算；冲突明确。 |
| 并发修改、A → C → A、交叉成环、祖先并发换绑 | 关系版本冲突明确、无环、三代快照一致。 |
| 事务中途失败 | 关系、计数、业务历史整体回滚，三代结算保持原子性。 |
| 管理员、普通用户与管理 API Key | 权限和操作者归因正确，既有用户展示范围不扩张。 |
| 存量完成、跳过、待处理业务 | 不重发终态；待处理使用可证明的原归属。 |
